Executive verdict

Use a modular monolith, not microservices. Keep FastAPI, LangGraph, Redis, Qdrant, and the existing Python feature packages. Introduce a small shared application boundary, explicit workflow results, and one authoritative progress model. More services or a framework rewrite would add coordination costs without addressing the root problems.

Preserve what already works

  • Separate ingestion, graph, memory, quiz, and database packages.
  • Explicit graph routing and an evidence gate before RAG generation.
  • Server-side quiz answer storage; grading does not need another LLM call.
  • Pydantic settings, a lockfile, Alembic groundwork, API contract tests, and an existing architecture guide.

Start with these decisions

  1. Single-user or multi-user? Current runtime state is global. Session ownership is not implemented just because database models exist.
  2. When is a chapter completed? Retry exhaustion currently advances progress even when validation failed.
  3. Which chat entry points are supported? FastAPI/CLI add memory; the direct LangGraph export does not.

For a private single-user tool, start with recommendations 2, 4, and 7. Before a multi-user rollout, recommendation 1 becomes a release prerequisite. Effort estimates below are relative implementation sizes, not measured delivery dates.

P1 / conditional 1. Make state ownership explicit before supporting multiple users

Evidence. Redis progress uses two fixed keys; chat uses chat:memory; Qdrant retrieval filters only on a shared metadata.seen flag. Quiz chapter selection reads that same global completion state and memory. Relational user/session/progress models are not wired into execution.

Consequence. Multiple callers share study position, conversation context, and eligible quiz material. A teach-start request resets the shared position. Adding session IDs only to Redis keys would still leave the shared Qdrant completion filter wrong.

Smallest complete change. If remaining single-user, document and enforce that deployment assumption. If supporting accounts, resolve a trusted owner/session context at each supported entry point; scope memory and quiz ownership to it. Keep Qdrant as a shared content index, not the authority for per-user completion. Prefer extending the existing SQLAlchemy model with completed chapters and transactional progress; use Redis for ephemeral memory/cache. Do not dual-write two independent progress authorities.

Migration guardrail. Existing global memory/progress cannot be reliably assigned to several users. Export or retain it, then explicitly assign it to one designated legacy session or start new sessions after confirmation. Do not silently drop it or distribute it to all users. Existing quiz caches can expire under their current TTL.

Reach. API, both CLIs, graph state/exports, memory keys, quiz lookup/cache, retrieval filters, SQL models/migration, UI session lifecycle, fixtures, and deployment documentation.

Acceptance. Two independent sessions can study, chat, reset, and take quizzes without changing each other's progress, memory, or eligible chapters. Access to a quiz is checked against its owner, not merely its ID. Size: large. Confidence: high; multi-user need is a product decision.

P1 2. Stop blocking FastAPI's event loop; own resource lifetimes

Evidence. Async chat and teach handlers call synchronous graph execution and Redis helpers directly. Graph nodes call synchronous model and Qdrant clients. Graphs are compiled in request paths despite module-level compiled exports. Embeddings are instantiated by every get_vector_store() call. Importing the memory package creates a service that immediately pings Redis.

Consequence. A slow model, embedding load, or datastore call blocks unrelated requests on that worker's event loop. Rebuilding clients/models adds avoidable work, and import-time I/O complicates isolated tests and startup behavior. No latency measurements were taken.

Smallest complete change. Keep the current synchronous graph implementation and offload the entire chat/study use case to FastAPI's threadpool, or make these handlers ordinary def endpoints. Include memory reads/writes, not just graph.invoke(). Reuse compiled graph definitions without request-local mutable state; manage reusable clients/embeddings in application lifespan, close them on shutdown, and configure supported client timeouts. Quiz already uses asyncio.to_thread; retain that pattern. Do not assume ainvoke() alone makes all custom nodes nonblocking.

Reach. API handlers, shared use cases, graph factories, embedder/store, memory initialization, startup/shutdown tests. Ensure reuse is safe for the chosen clients and bound threadpool admission rather than allowing unlimited expensive jobs.

Acceptance. Under a deliberately delayed fake chat/study workflow, a simultaneous lightweight request still completes before that workflow finishes. A lifecycle test confirms one embedding initialization per application lifetime and cleanup of owned clients. Size: medium. Confidence: high.

Sources: frontend/server.py:36,43,115,124,142; graph/graph_builder.py:153; ingestion/store.py:35; ingestion/embedder.py:19; memory/__init__.py:15; memory/chat_memory.py:39,48; quiz/quiz_service.py:417.

P1 3. Treat chapter completion as one recoverable state transition

Evidence. Completion writes each Qdrant chunk first, then writes module and chapter through separate Redis commands. Next-chapter discovery fetches a full chapter and assumes the next module starts at chapter 1. Memory compaction reads a list, then deletes/rebuilds it later; its write pipeline does not protect the earlier read.

Consequence. A failure can leave partial seen flags or a mixed module/chapter pair. Overlapping requests can race. A concurrent chat append can be lost when compaction replaces an older snapshot. A process-local quiz lock does not coordinate these operations or multiple workers.

Smallest complete change. For single-user Redis persistence, update position atomically and protect chapter advancement with a version check or compare-and-set; protect compaction's read-modify-write with Redis WATCH/retry or an equivalent server-side operation. For the multi-user target, commit completion and next position in one SQL transaction with a version/row lock. Derive studied eligibility from that authority so Qdrant flags are no longer part of the commit. Add a small chapter catalog query instead of loading an entire next chapter solely to test existence.

Migration guardrail. Redis and Qdrant cannot share a normal transaction. Until completion is moved to one authority, make cross-store updates idempotent and explicitly reconcilable; a Redis transaction alone does not solve partial Qdrant writes. Do not add an outbox/event platform unless the remaining cross-store requirements justify it.

Reach. Study nodes, progress helpers, content store, chat-memory compaction, reset behavior, persistence tests and, if selected, the SQL migration.

Acceptance. Fault injection after each write leaves either the old state or a recoverable recorded transition. Two requests starting from the same version cannot both advance it. An append during compaction is retained. Missing chapter numbers/end-of-catalog produce explicit outcomes. Size: medium to large. Confidence: high.

Sources: graph/study_nodes.py:274,301,304,322; ingestion/store.py:152; memory/progress.py:43,55; memory/chat_memory.py:240; quiz/quiz_service.py:51,423.

P1 4. Give study validation one policy and explicit terminal results

Evidence. Summary generation requests 50-80% of concatenated input length; validation accepts 50-75% of summed chunk metadata lengths. The formulas and bases differ. Summary retry exhaustion routes to update_progress regardless of the validation flag. Teach endpoints infer done from an empty summary.

Consequence. A response can follow the generation prompt yet fail validation. Exhausted invalid summaries still mark material studied, while the API cannot distinguish validation failure, unavailable content, and normal completion. Overlapping chunks also make chunk-length sums an imperfect measure of original chapter length.

Smallest complete change. Define the accepted length rule once and use the same text basis in generation and validation. Run deterministic length checks before buying another quality-validation call. Return a small typed outcome such as completed, validation_failed, or no_material, plus the served chapter and retry count. Do not advance on failure by default; if accepting imperfect summaries is desired, make that an explicit, surfaced product policy. Do not silently change the current completion behavior in a refactor.

Reach. Study nodes and routing, state/result schema, teach responses, UI completion/error display, CLI output, diagrams/docs, graph and API fixtures.

Acceptance. Boundary tests cover minimum-1, minimum, maximum, maximum+1, empty input, and exhausted retries. Progress changes only for the chosen success policy, and the API returns the actual chapter served rather than a separately read, potentially stale position. Size: medium. Confidence: high.

Sources: graph/study_nodes.py:71,112,124,196,208,274; graph/graph_builder.py:64,103; frontend/server.py:108,124,142.

P1 5. Validate generated quiz data before caching or grading it

Evidence. Quiz generation accepts a parsed list without validating each question. API fields use list[dict]; the count has no range constraint. Grading compares answers.get(id, "") against q.get("correct_answer", ""). Broad API catches turn all generation failures into 400 and all submission failures into 404.

Consequence. Parseable but malformed model output can reach the UI/cache. A missing correct answer and an unanswered question both become empty strings and compare equal. Invalid count values and operational outages are not cleanly distinguished from user errors. Generated totals may also be lower than requested after selection or generation shortfalls.

Smallest complete change. Add Pydantic models for generated/cached questions and public questions: nonempty text, exactly A-D options, and a correct answer that references an option. Prefer provider-supported structured output; if the selected model does not support it, retain one bounded parse/repair path followed by the same validation. Bound requested counts according to model capacity and reject invalid requests at the API boundary. Grade only validated cached quizzes; invalidate/report incompatible old cache entries. Map known domain errors separately from logged dependency/server failures. Do not silently label unexpected failures as bad input.

Reach. Quiz parser/generator/cache/grader, request/response models, UI error handling, API and grading tests. Preserve the separation between private answers and public questions. Explicitly decide whether partial quizzes are allowed; return an explicit partial outcome if so.

Acceptance. Missing answers, invalid options, scalar list items, wrong counts, invalid cache payloads, and expired quizzes have deterministic results; unanswered questions never earn marks because an answer key is absent. Invalid counts return 422; dependency outages are not returned as 400/404. Size: medium. Confidence: high.

Sources: frontend/server.py:53,57,77,93; quiz/quiz_service.py:192,294,353,450,493,501,520,563; tests/test_quiz_grading.py:31.

P2 6. Share use-case orchestration and narrow dependency seams

Evidence. FastAPI, the main CLI, and interactive CLI each format chat memory, invoke the graph, and persist the turn. The exported chat graph only runs nodes and does not perform that caller-side memory orchestration. Both graphs use one all-required StudyState despite callers supplying partial state. Quiz code independently implements Qdrant scrolling/search, bypassing ingestion.store; its topic-search exceptions are silently ignored.

Consequence. Chat behavior differs by entry point. Query filters, embedding behavior, and error policy can diverge between quiz and chat. Tests replace a module in sys.modules instead of injecting a small dependency. The state contract overstates required inputs and mixes unrelated workflow fields.

Smallest complete change. Extract the existing chat wrapper into one use-case function and call it from FastAPI/CLI. For the LangGraph API, either include equivalent memory load/save nodes in the exported workflow or explicitly document it as a stateless, caller-managed API; do not make a workflow call itself through a use-case wrapper. Add shared content-store operations for the queries quiz actually needs, then use the same embedding/search path and error reporting. Separate chat and study input/state/output types, mark optional intermediates accurately, and annotate compiled graph return types correctly.

Reach. All three chat callers, graph exports/manifest contract, state types, quiz/store queries, dependency injection in tests, and usage docs. Keep current HTTP response shapes until an intentional contract change is introduced.

Acceptance. The same fake dependencies produce equivalent chat/memory behavior on each supported entry point. Quiz topic matching demonstrably uses the configured embedding path and reports failures. Type checking validates partial graph inputs without broad casts. Size: medium. Confidence: high.

P2 7. Make ingestion repeatable, ordered, and embedding-compatible

Evidence. upsert_chunks() calls add_documents(chunks) without stable IDs or a source-replacement policy. The loader sets seen=False on ingested material. Chunk indices are stored, but chapter fetches return Qdrant scroll order without sorting by those indices. Vector dimension is fixed at 384 while the embedding model is configurable.

Consequence. The application itself cannot guarantee re-ingestion replaces existing content or removes stale chunks. Fresh copies can coexist with old seen/unseen state. Summary input and the quiz's truncated first chunks need not follow chapter reading order. An alternate embedding model can be incompatible with the existing vector schema; matching dimension alone also does not imply matching embedding space.

Smallest complete change. Define a portable source/chapter identifier and versioned chunk IDs; use explicit IDs and a scoped stale-chunk cleanup policy. Sort chapter content by stored chunk index before summaries or truncation. Validate model identity and dimension against collection metadata, not just a hard-coded constant. Changing models requires a new/versioned collection and complete re-embedding, not reusing old vectors. Keep user completion separate from corpus replacement as recommended above.

Migration guardrail. Inspect/export the current collection first. Build the new version alongside it, validate counts and retrieval, then switch configuration; never delete the live collection as an initial cleanup step. Surface source files that yield zero valid chunks instead of treating silent loss as successful ingestion.

Reach. Loader metadata, chunker, pipeline/store, quiz chapter reads, collection configuration, migration/runbook, ingestion tests.

Acceptance. Ingesting identical input twice preserves IDs and point count. Editing a source leaves no stale chunks in its active version. Shuffled storage results reconstruct the original sequence. Incompatible model/collection pairs fail clearly before writes. Size: medium. Confidence: high for missing guarantees; no live collection inspection performed.

Sources: ingestion/store.py:28,35,55,65; ingestion/loader.py:134; ingestion/chunker.py:145; ingestion/pipeline.py:58; quiz/quiz_service.py:375; config/settings.py:36.

P2 9. Make configuration and operational outcomes truthful

Evidence. Quiz TTL/count settings exist, but quiz code uses a constant/default; Ollama URL/model fields are not directly passed by the graph code. Graph nodes mostly print; quiz mixes logging and print, and topic search swallows exceptions. FastAPI serves static assets, while the LangGraph manifest serves only graph endpoints. There are no explicit application health/readiness endpoints in the reviewed server.

Smallest complete change. Wire supported settings through one construction path, or remove/deprecate redundant knobs and document provider-specific configuration accurately. Add structured logs with request/run ID, served chapter, retry count, dependency failures, and timings without logging raw conversation content by default. Distinguish readiness from liveness and define which dependencies are required versus optional. Document FastAPI/UI and LangGraph as separate deployment surfaces; configure the production ASGI command rather than using the reload-enabled development entry point.

Reach. Settings, model/client initialization, quiz defaults/cache TTL, API error mapping, observability, environment template, README and deployment docs. Keep tracing optional and avoid sending private conversation content to third-party telemetry without an explicit policy.

Acceptance. Overridden TTL/count/provider settings affect behavior in unit tests. Dependency failure logs identify the failing operation, and readiness reflects required-service availability without invoking the LLM on every probe. Both documented deployment commands expose exactly their promised endpoints. Size: small to medium. Confidence: high.

P3 10. Split UI responsibilities only where behavior benefits

Evidence. One React source module holds chat, teaching, quiz generation, submission, review, and retry. Fetch/error parsing is repeated; quiz generation is implemented in both the app and overlay. Loading state is represented by several independent booleans. Quiz choices are clickable labels rather than native radio inputs, and the overlay has no dialog/focus-management semantics.

Smallest complete change. Extract the existing quiz overlay into its own component and reuse one small API request helper with the backend's explicit error schema. Move feature behavior into focused hooks only if needed after that extraction. Use native radio groups for answers and an accessible dialog with focus entry, Escape handling, and focus restoration. Keep React state; no global state library or frontend framework rewrite is justified.

Reach. React app/quiz component, CSS, API error responses, UI tests, rebuilt static assets. Preserve existing source citations and don't start rendering arbitrary model HTML.

Acceptance. Keyboard-only users can open, answer, submit, and close a quiz with predictable focus. Generation/retry errors retain a coherent screen state; duplicate submit is prevented; the UI and backend agree on partial/exhausted outcomes. Size: small to medium. Confidence: high.
